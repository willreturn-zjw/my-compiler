# 全流程测试过程

## 1. 测试范围

测试清单中的 30 条用例按编译流水线分成两组，并由 pytest 参数化执行：

- TC01–TC15：SysY 源码到 Koopa IR，以及 IR 构造和数据流分析相关行为；
- TC16–TC30：Koopa IR/前端生成结果到 ARMv8 汇编的静态生成行为。

本轮测试不执行 ARMv8 汇编。后端结果通过汇编文本检查验证，因此不要求本机具有 AArch64 汇编器、链接器或运行环境。

## 2. 执行前置条件

1. 在 Linux/WSL/AArch64 目标环境准备可执行的编译器程序，或者先按 README 的构建说明完成构建；
2. 确认编译器支持 `-S <input> -o <output>` 调用形式；
3. 使用 Python 3.9 或更高版本并安装 pytest；
4. 如果需要排查单条用例，启用 `--keep-artifacts` 保留中间文件。

## 3. 单条用例流程

每条参数化用例都按相同流程执行：

1. 创建唯一临时目录；
2. 写入该用例的 SysY 输入；
3. 在该目录中调用编译器，隔离项目固定生成的 `parse.kp`；
4. 检查编译器退出码和预期文件是否生成；
5. 前端用例检查 `parse.kp`，后端用例同时检查 `parse.kp` 和 `.s` 文件；
6. 使用用例的正则断言检查 IR 指令、ARMv8 指令、寄存器、标签、数据段和访存模式；
7. 记录状态、耗时和失败原因，然后删除临时目录，除非指定保留产物。

## 4. 状态判定

- `PASS`：编译器正常退出，预期文件存在，所有静态断言满足，禁止模式未出现；
- `FAIL`：编译器异常退出、超时、输出文件缺失或静态断言不满足；
- `BLOCKED`：当前环境无法运行指定编译器，例如缺少可执行文件、文件存在但其 ELF 解释器/动态库不可用，或目标架构不匹配。pytest 界面显示为 `SKIPPED`，汇总报告统一记为 `BLOCKED`。

`BLOCKED` 不等价于通过，也不等价于编译器缺陷。它表示需要补充构建或运行环境后重试。脚本仅在存在 `FAIL` 时返回退出码 1；存在 `BLOCKED` 时返回 0，并在报告中单独统计。

## 5. 结果产物

默认输出目录为 `test-results/`：

- `results.md`：面向人工评审的用例结果表；
- `results.csv`：便于 Excel 汇总和筛选；
- `results.json`：便于 CI 或其他程序读取；
- `artifacts/TCxx/`：仅在启用 `--keep-artifacts` 时生成，包含输入、`parse.kp`、汇编和诊断信息。

## 6. 测试完成标准

在目标构建环境中，30 条用例均应完成执行；不存在 `FAIL`；所有 `BLOCKED` 都有明确的环境原因并在补齐环境后复测。后端静态测试通过后，如需证明运行时语义，还应在具备 AArch64 环境时另行执行汇编、链接和运行测试。
